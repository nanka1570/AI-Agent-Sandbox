# 技術仕様書 (Architecture Design Document)

## テクノロジースタック

### 言語・ランタイム

| 技術 | バージョン |
|------|-----------|
| Node.js | v20.x LTS以上 |
| TypeScript | 5.x |
| npm | 10.x以上 |

- **Node.js v20.x LTS以上**
  - LTSによる長期サポートで安定性を確保
  - クロスプラットフォーム対応（macOS、Linux、Windows）
  - PRDで定義した対応バージョン要件を満たす

- **TypeScript 5.x**
  - 静的型付けにより、データモデル（Task、TaskStore等）の整合性をコンパイル時に検証
  - IDE補完により開発効率を向上
  - 機能設計書で定義した型定義をそのまま実装コードに利用可能

- **npm 10.x以上**
  - Node.js v20.x以上に標準搭載
  - package-lock.jsonによる依存関係の厳密な管理

## アーキテクチャパターン

### レイヤードアーキテクチャ

```
┌─────────────────────────────────────────┐
│   CLIレイヤー (commands/)                │ ← コマンド解析、入力バリデーション、結果表示
├─────────────────────────────────────────┤
│   サービスレイヤー (services/)            │ ← ビジネスロジック（タスク管理、Git連携）
├─────────────────────────────────────────┤
│   データレイヤー (services/storage.ts)    │ ← JSONファイルの読み書き
└─────────────────────────────────────────┘
```

#### CLIレイヤー（commands/）
- **責務**: Commander.jsによるコマンド定義、ユーザー入力のバリデーション、TaskServiceの呼び出し、結果のフォーマット・表示
- **許可される操作**: サービスレイヤーの呼び出し、ユーティリティ関数の利用
- **禁止される操作**: データレイヤー（Storage）への直接アクセス、ファイルシステムへの直接操作

#### サービスレイヤー（services/）
- **責務**: タスクのCRUDビジネスロジック、ステータス遷移管理、Git操作の実行
- **許可される操作**: データレイヤーの呼び出し、外部ライブラリ（simple-git）の利用
- **禁止される操作**: CLIレイヤーへの依存（標準出力への直接書き込み等）

#### データレイヤー（services/storage.ts）
- **責務**: `.taskcli/tasks.json`の読み書き、アトミック書き込みの保証
- **許可される操作**: ファイルシステムへのアクセス
- **禁止される操作**: ビジネスロジックの実装、データの加工・変換

### 依存関係の方向

```
commands/ → services/TaskService → services/Storage
                ↓
           services/GitService → simple-git → Git CLI
```

すべての依存は上位レイヤーから下位レイヤーへの一方向のみ。循環依存は禁止。

## データ永続化戦略

### ストレージ方式

| データ種別 | ストレージ | フォーマット | 理由 |
|-----------|----------|-------------|------|
| タスクデータ | ローカルファイル | JSON（インデント付き） | 特別なソフトウェア不要。人間が直接読み書きでき、Gitでの差分確認も容易 |
| 設定データ | （P1で対応） | JSON | GitHub Tokenなどの設定はP1で扱う |

### ファイル構成

```
<プロジェクトルート>/
└── .taskcli/
    └── tasks.json       # タスクデータ（TaskStore形式）
```

### アトミック書き込み

データの安全性を保証するため、書き込みはアトミックに行う:

1. 一時ファイル `.taskcli/tasks.json.tmp` に全データを書き込む
2. `fs.renameSync()` で一時ファイルを `tasks.json` にリネーム
3. `renameSync`は同一ファイルシステム上でアトミックなため、書き込み途中のクラッシュでもデータが破損しない

### バックアップ戦略

- **方式**: Gitでの管理をユーザーに推奨（`.taskcli/`をGit管理下に置くかどうかはユーザー判断）
- **自動バックアップ**: MVPでは実装しない。JSONファイルのアトミック書き込みでデータ破損を防止
- **復元方法**: Gitの履歴から復元、または`tasks.json`を手動で編集

## パフォーマンス要件

### レスポンスタイム

| 操作 | 目標時間 | 測定環境 |
|------|---------|---------|
| タスク追加 (`task add`) | 100ms以内 | ローカルファイルI/Oのみ |
| タスク一覧 (`task list`) - 100件 | 100ms以内 | ローカルファイルI/Oのみ |
| タスク一覧 (`task list`) - 1,000件 | 1秒以内 | ローカルファイルI/Oのみ |
| タスク開始 (`task start`) | 500ms以内 | ファイルI/O + Gitブランチ作成 |
| タスク完了 (`task done --merge`) | 2秒以内 | ファイルI/O + Gitマージ |

**測定方法**: `process.hrtime.bigint()`でCLI起動から結果表示まで計測

### リソース使用量

| リソース | 上限 | 理由 |
|---------|------|------|
| メモリ | 50MB | CLIツールとして妥当な上限。タスク1,000件のJSON読み込みでも数MB程度 |
| ディスク | 10MB | tasks.json単体。タスク10,000件でも数MB以内 |

## セキュリティアーキテクチャ

### データ保護

- **ファイルパーミッション**: `.taskcli/tasks.json`は通常のパーミッション（644）で作成。MVPでは機密情報を含まないため、厳格なパーミッション制御は不要
- **機密情報管理（P1）**: GitHub Personal Access Tokenは`~/.taskcli/config.json`にパーミッション600で保存、または環境変数`TASKCLI_GITHUB_TOKEN`で管理

### 入力検証

- **タスクタイトル**: 1〜200文字。空文字・超長文字列を拒否
- **タスクID**: 正の整数のみ許可。`parseInt()`の結果が`NaN`や負数の場合はエラー
- **ブランチ名サニタイズ**: タイトルから生成するブランチ名は英数字・ハイフンのみに変換し、シェルインジェクションやGitの不正なref名を防止
- **日付フォーマット**: `--due`オプションは`YYYY-MM-DD`形式のみ許可

### エラーハンドリング

- ユーザー向けエラーメッセージにスタックトレースを含めない
- 内部エラーの詳細はログに出力し、ユーザーには対処方法を提示
- 未知のエラーは「予期しないエラーが発生しました。問題が続く場合はIssueを報告してください」と表示

## スケーラビリティ設計

### データ増加への対応

- **想定データ量**: 通常利用で100〜500件。最大10,000件までの動作を保証
- **パフォーマンス劣化対策**: JSONファイルの全件読み込み方式のため、10,000件を超えるとパフォーマンスが劣化する可能性がある。必要に応じて将来SQLiteに移行可能な設計とする（StorageクラスのインターフェースをDB非依存に保つ）
- **アーカイブ戦略**: `task archive`で完了済みタスクをアーカイブステータスに変更。`task list`のデフォルト表示からは除外される

### 機能拡張性

- **プラグインシステム**: MVPでは実装しない。将来的にはコマンドの追加・フックの差し込みを可能にする設計を検討
- **設定のカスタマイズ**: P1でconfigファイル（`~/.taskcli/config.json`）を導入予定。デフォルトブランチ名のプレフィックス変更などを想定
- **Storage抽象化**: StorageクラスのインターフェースをJSON固有の実装から分離し、将来的にSQLite等への移行を容易にする

## テスト戦略

### ユニットテスト
- **フレームワーク**: Vitest
- **対象**: TaskService（ビジネスロジック）、Storage（ファイルI/O）、ユーティリティ関数（ブランチ名生成、テーブルフォーマット等）
- **カバレッジ目標**:
  - サービスレイヤー（TaskService, GitService）: 80%以上
  - データレイヤー（Storage）: 90%以上（データ損失防止のため高めに設定）
  - ユーティリティ（generateBranchName等）: 90%以上
  - CLIレイヤー: E2Eテストで補完するため60%以上

### 統合テスト
- **方法**: TaskService + Storage の結合テスト。テスト用の一時ディレクトリでファイルI/Oを実行
- **対象**: タスクのライフサイクル（作成→一覧→開始→完了→アーカイブ→削除）

### E2Eテスト
- **ツール**: Vitest + `child_process.execSync`でCLIバイナリを実行
- **シナリオ**: 基本フロー（add → list → start → done）、エラーケース（不正入力、存在しないID）

## 技術的制約

### 環境要件
- **OS**: macOS、Linux、Windows（Git Bash / WSL含む）
- **最小メモリ**: 128MB（Node.jsランタイム含む）
- **必要ディスク容量**: 50MB（`node_modules`含む。グローバルインストール時）
- **必要な外部依存**: Node.js 20.x以上、Git 2.30以上（ブランチ連携機能使用時）

### パフォーマンス制約
- JSONファイルの全件読み込み方式のため、タスク10,000件超でレスポンスタイム増加の可能性
- Git操作（ブランチ作成・マージ）はGit CLIの実行速度に依存

### セキュリティ制約
- GitHub Token等の機密情報はP1まで対応しない（MVPではローカルデータのみ）
- ローカルファイルのため、OSレベルのファイルパーミッションに依存

## 依存関係管理

| ライブラリ | 用途 | バージョン管理方針 |
|-----------|------|-------------------|
| commander | CLIフレームワーク | `^14.0.0`（マイナーバージョンまで自動更新） |
| simple-git | Git操作 | `^3.0.0`（マイナーバージョンまで自動更新） |
| cli-table3 | テーブル表示 | `^0.6.0`（マイナーバージョンまで自動更新） |
| chalk | 色付き出力 | `^5.0.0`（ESM版を使用。メジャーバージョン固定） |
| vitest | テスト（dev） | `^2.0.0`（開発依存のためマイナーまで自動更新） |
| typescript | コンパイラ（dev） | `~5.3.0`（パッチバージョンのみ自動更新） |
| eslint | リンター（dev） | `^9.0.0`（Flat Config対応版） |
| prettier | フォーマッター（dev） | `^3.0.0`（マイナーまで自動更新） |
| husky | Gitフック（dev） | `^9.0.0`（マイナーまで自動更新） |
| lint-staged | ステージング連携（dev） | `^15.0.0`（マイナーまで自動更新） |

**方針**:
- 本番依存（dependencies）はキャレット（^）でマイナーバージョンまで自動更新を許可
- TypeScriptはチルダ（~）でパッチバージョンのみ自動更新（コンパイラの挙動変更リスクを軽減）
- `package-lock.json`で全依存のバージョンを固定し、再現可能なビルドを保証
