## 1. 目的・背景

### 1.1 現状（MVP完了）

Phase 0〜5b が完了し、以下のMVPが動作する状態。

| 項目 | 内容 |
|------|------|
| ページ数 | 4ページ（ダッシュボード、クレカ管理、給料管理、支払い管理） |
| データモデル | Salary, CreditCard, Payment の3テーブル |
| DB | SQLite（ローカルファイル） |
| 認証 | なし（単一ユーザー） |
| デプロイ | なし（localhost のみ） |
| テスト | 82件全PASS（Vitest 79件 + Playwright E2E 3件） |
| デザイン | Neo-Brutalism（Retro Pop Edition） |

### 1.2 Phase B の目標

MVPを**無料公開して広告収益を得る**レベルまで機能・品質を上げる。

- マルチユーザー対応（認証 + クラウドDB）
- カテゴリ・予算管理で家計簿としての実用性向上
- PWA対応でスマホアプリのような体験を提供
- 広告を組み込んで収益化

## 2. ターゲットユーザー

**メモ帳で家計簿を管理していた人**

| 特徴 | 対応方針 |
|------|---------|
| 複雑な設定は苦手 | 初回ログインでデフォルトカテゴリ自動作成、設定不要で使い始められる |
| 「パッと書いて終わり」が習慣 | クイック入力（金額+カテゴリだけで即登録）を提供 |
| スマホで使いたい | PWA対応でホーム画面に追加、アプリのように使える |
| 何にいくら使ったか知りたい | カテゴリ別集計 + 予算消化率で「使いすぎ」を可視化 |

### フェーズ依存関係

```
Phase 6 (基盤) ← 全ての前提
  |
  ├─→ Phase 7 (カテゴリ+予算)
  |     ├─→ Phase 8 (UX改善) ← カテゴリが必要
  |     └─→ Phase 11 (レポート) ← カテゴリ+予算データが必要

  ├─→ Phase 9 (PWA) ← デプロイ済みが前提
  └─→ Phase 10 (収益化) ← デプロイ済みが前提
```

Phase 9・10 は Phase 7・8 と並行実施可能。

## 4. 各フェーズの詳細

### Phase 6: 基盤構築（認証 + DB移行 + デプロイ）

**なぜ必要**: 公開の前提条件。認証なしではマルチユーザー不可、SQLiteではVercelにデプロイ不可。後続の全フェーズの土台となる。

#### Phase 6a: Supabase + DB移行（SQLite → PostgreSQL）

| 項目 | 内容 |
|------|------|
| やること | Prisma の datasource を SQLite → PostgreSQL に変更。Supabase プロジェクト作成。全テーブルに `userId` カラムを追加 |
| 変更ファイル | `prisma/schema.prisma`, `src/lib/db.ts` |
| 技術 | Supabase PostgreSQL, `@prisma/adapter-pg` |

**DB変更**:

```
全テーブル共通:
  + userId  String  // Supabase Auth の user.id
  + @@index([userId, month])  // クエリ高速化
```

#### Phase 6b: Supabase Auth 認証

| 項目 | 内容 |
|------|------|
| やること | メールアドレス + パスワード認証を実装。ログイン/登録/ログアウト/パスワードリセットの4機能 |
| 新規ページ | `/login`, `/register`, `/forgot-password` |
| 新規ファイル | `src/lib/supabase.ts`（クライアント生成）, `middleware.ts`（認証チェック） |
| 技術 | `@supabase/supabase-js`, `@supabase/ssr` |

**動作仕様**:
- 未認証ユーザー → `/login` にリダイレクト
- ログイン後 → ダッシュボード（`/`）に遷移
- ヘッダーにログアウトボタン追加

#### Phase 6c: RLS + Server Actions改修

| 項目 | 内容 |
|------|------|
| やること | Supabase RLS（Row Level Security）を設定。全Server Actionsに `userId` フィルタを追加 |
| 変更ファイル | `src/lib/actions/credit-card.ts`, `salary.ts`, `payment.ts`, `src/app/page.tsx` |
| 技術 | Supabase RLS ポリシー |

**RLSポリシー**:
- 各テーブルで `auth.uid() = userId` のポリシーを設定
- ユーザーは自分のデータのみ読み書き可能

#### Phase 6d: Vercel デプロイ

| 項目 | 内容 |
|------|------|
| やること | Vercelプロジェクト作成、環境変数設定（`DATABASE_URL`, `SUPABASE_URL`, `SUPABASE_ANON_KEY`）、本番ビルド確認 |
| 変更ファイル | `next.config.ts`（必要に応じて） |
| 技術 | Vercel |

### Phase 8: UX改善（メモ帳ユーザー向け）

**なぜ必要**: ターゲットの「メモ帳ユーザー」は「パッと書いて終わり」が習慣。ダイアログを開いて複数項目を入力するのは面倒。操作が面倒だとアプリから離脱する。

#### Phase 8a: クイック入力

| 項目 | 内容 |
|------|------|
| やること | ダッシュボード右下にFAB（Floating Action Button）を配置。タップでボトムシート風のクイック入力フォームを表示。金額 + カテゴリだけで支出登録完了 |
| 変更ページ | `/`（ダッシュボード） |
| 新規コンポーネント | `QuickInputFab`, `QuickInputSheet` |

**操作フロー**:
1. FABボタン（+）をタップ
2. ボトムシートが開く
3. 金額を入力、カテゴリを選択
4. 「登録」をタップ → トースト通知 → シート閉じる

#### Phase 8b: 検索・フィルター強化

| 項目 | 内容 |
|------|------|
| やること | 支払い一覧にカテゴリフィルター、金額範囲フィルター、キーワード検索（メモ内容）を追加 |
| 変更ページ | `/payments` |
| 変更コンポーネント | `PaymentList` |

#### Phase 8c: 繰り返し支払い

| 項目 | 内容 |
|------|------|
| やること | 支払い登録時に「毎月繰り返し」チェックを追加。翌月以降の固定費（家賃、サブスク等）を自動生成 |
| 変更テーブル | `Payment` に `isRecurring`, `recurringGroupId` 追加 |
| 変更ページ | `/payments` |

**DB変更（Payment テーブル）**:

```
Payment:
  + isRecurring      Boolean  @default(false)  // 繰り返しフラグ
  + recurringGroupId String?                     // 繰り返しグループID
```

### Phase 9: PWA対応

**なぜ必要**: スマホでホーム画面に追加 → アイコンタップで即起動。ブラウザを開いてURLを入力する手間がなくなる。ネイティブアプリ開発なしでアプリのような体験を提供できる。

| 項目 | 内容 |
|------|------|
| やること | PWAライブラリ導入、マニフェスト作成、サービスワーカー登録、オフラインフォールバック、アプリアイコン作成 |
| 新規ファイル | `public/manifest.json`, `public/icons/`（各サイズ）, `/offline` ページ |
| 変更ファイル | `next.config.ts`, `src/app/layout.tsx` |
| 技術 | `next-pwa` または `@ducanh2912/next-pwa`（Next.js 16対応を要確認） |

**PWAで実現すること**:
- ホーム画面にアプリアイコン追加
- フルスクリーン表示（ブラウザバー非表示）
- オフライン時のフォールバックページ表示

**なぜ必要**: 広告は「無料公開して収益を得る」ビジネスモデルの根幹。法的ページはAdSense審査の必須条件。CSVエクスポートは「データを人質に取られている」という不安を解消し、ユーザーの信頼感を高める。

|------|------|
| やること | Google AdSense申請、広告ユニット作成、レイアウトへの広告スロット配置 |
| 変更ファイル | `src/app/layout.tsx`（スクリプト追加）、各ページ |
| 技術 | Google AdSense |

**広告配置案**:
- ダッシュボード: グラフ下に横長バナー（728x90）
- モバイル: セクション間にインフィード広告

#### Phase 10b: CSVエクスポート

**CSVフォーマット**:

**なぜ必要**: ダッシュボードは「今月」のスナップショット。レポートは「この1年でどう変わったか」を見せる。「去年と比べて食費が2万円減った」のような気づきが、継続利用のモチベーションになる。

| 項目 | 内容 |
|------|------|
| やること | 月次/年次の分析レポートページを作成 |
| 新規ページ | `/reports` |
| ナビ追加 | BottomNav に「REPORTS」追加 |
| 技術 | Recharts（既存） |

**月次レポート**:
- カテゴリ別支出内訳（円グラフ）
- 前月比較（増減表示）
- 予算達成率

**年次レポート**:
- 月別支出推移グラフ（折れ線グラフ）
- 年間支出合計
- カテゴリ別年間ランキング

## 7. やらないこと（スコープ外）

| 機能 | 除外理由 |
|------|---------|
| ダークモード | Neo-Brutalism のデザインシステム全体に `.dark` バリアント追加が必要で工数大。ユーザーからの要望が出てから対応 |
| 多言語対応（i18n） | ターゲットが日本語ユーザー限定。全テキストの外部化は工数膨大。海外展開を決めてから対応 |
| TanStack Query | 現在の Server Components + revalidatePath パターンで十分。楽観的更新が必要になったら検討 |
| CSVインポート | フォーマット不正、重複検知などエッジケースが多い。エクスポートのみ先行し、要望が出てから対応 |
| 通知・リマインダー | プッシュ通知はサービスワーカー + バックエンド cron が必要で実装コスト高。PWA対応後に検討 |
| 家族共有 | 権限管理（閲覧のみ/編集可）が必要で設計が大幅に変わる。個人利用で十分な段階 |
| 銀行口座連携 | Fintech APIとの連携は法規制・セキュリティ要件が個人開発の範囲を超える |

## 8. 開発方式

各フェーズ内でMVPと同じ**厳密ウォーターフォール**を適用する。

| 工程 | 内容 |
|------|------|
| 設計 | 既存設計書を更新（DB設計書、画面設計書、詳細設計書、テスト仕様書） |
| 実装 | 設計に基づいてコーディング |
| テスト | 既存テスト更新 + 新規テスト追加 |

フェーズ間は順次進行（Phase 6 完了 → Phase 7 開始）とする。
ただし Phase 9・10 は Phase 7・8 と並行実施可能。
