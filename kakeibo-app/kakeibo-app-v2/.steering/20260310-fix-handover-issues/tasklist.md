# タスクリスト

## 🚨 タスク完全完了の原則

**このファイルの全タスクが完了するまで作業を継続すること**

### 必須ルール
- **全てのタスクを`[x]`にすること**
- 「時間の都合により別タスクとして実施予定」は禁止
- 「実装が複雑すぎるため後回し」は禁止
- 未完了タスク（`[ ]`）を残したまま作業を終了しない

### 実装可能なタスクのみを計画
- 計画段階で「実装可能なタスク」のみをリストアップ
- 「将来やるかもしれないタスク」は含めない
- 「検討中のタスク」は含めない

### タスクスキップが許可される唯一のケース
以下の技術的理由に該当する場合のみスキップ可能:
- 実装方針の変更により、機能自体が不要になった
- アーキテクチャ変更により、別の実装方法に置き換わった
- 依存関係の変更により、タスクが実行不可能になった

スキップ時は必ず理由を明記:
```markdown
- [x] ~~タスク名~~（実装方針変更により不要: 具体的な技術的理由）
```

### タスクが大きすぎる場合
- タスクを小さなサブタスクに分割
- 分割したサブタスクをこのファイルに追加
- サブタスクを1つずつ完了させる

- `report.test.ts`: getReportData が Prisma に直接依存しており、DB接続なしの単体テストが不可能なため

### 学んだこと

**技術的な学び**:
- PRDのデータモデル定義（sortOrderの用途説明）がコードの設計判断に直結する。重複チェックのような制約はPRDとの整合性を常に確認すべき
- 資金繰りロジックでは、同一カードでも利用月が異なれば引き落とし日が変わるケースがある。基準月で一括計算するのではなく、各支払いの実際の利用月から算出する必要がある
- Vitest + Zod v4 の組み合わせでは `zod/v4` サブパスインポートがそのまま動作する

**プロセス上の改善点**:
- developer サブエージェント2並列でテスト作成を効率化できた（ユーティリティ + バリデーション）

### 次回への改善提案
- 単体テストはMVP実装と同時に作成すべき（後付けだとテスト対象のコード理解に時間がかかる）
- PRDとコードの整合性チェックをレビュー項目に含めるべき
