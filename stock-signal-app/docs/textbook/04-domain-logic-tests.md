# 第4章 ドメインロジックと単体テスト（Vitest）

この章が本アプリの心臓部です。時間をかけてください。

## 学習目標

- SMA・RSI を数式からコードに書き起こせる
- Vitest で単体テストを書き、「テストが仕様書になる」状態を作れる
- 「どんなテストを書くべきか」を自分で設計できる（既知値・境界値・性質）

## facility-management との接続

facility-management にはテストがありませんでした。「画面を触って確認」で成立していたのは、ロジックが単純（CRUD + 重複チェック）だったからです。RSI の計算が正しいかは画面を見ても分かりません——**目視で検証できないロジックを持った時点で、単体テストは義務**になります。

## 本編

### 1. 数式 → コード: SMA（単純移動平均）

SMA は「直近 N 日の終値の平均」です。全期間分を一度に計算し、データ不足の先頭は `null` にします。

```
入力: [1, 2, 3, 4, 5], 期間 3
出力: [null, null, 2, 3, 4]   ← 3日分たまって初めて平均が出る
```

素朴に書くと「各位置で N 個を足す」= O(n×N) ですが、**移動窓**（新しい値を足し、窓から出た値を引く）で O(n) になります。見本 `lib/indicators/sma.ts` は 20 行なので、まず自分で書いてから読み比べてください。

設計上の決めごと（こういう小さな決定を自分で下すのが設計です）:
- 戻り値の長さは入力と同じ（`null` 埋め）— インデックスが日付とずれない
- `period < 1` は例外を投げる — 呼び出し側のバグを早期に検出

### 2. 数式 → コード: RSI（相対力指数）

RSI は「直近 N 日の値動きのうち上昇分が占める割合」を 0〜100 で表します。Wilder 方式:

```
1. 前日比を上昇幅(gain)と下落幅(loss)に分ける
2. 初期値: 最初の N 本の gain・loss の単純平均
3. 以降: avgGain = (前回avgGain × (N-1) + 今日のgain) / N   ← 平滑化
4. RSI = 100 − 100 / (1 + avgGain / avgLoss)
```

エッジケースを**先に**決めます: `avgLoss = 0`（下落が一度もない）のとき除算できない → 慣例で RSI = 100 とする。こういう「数式に書いていない端っこ」を決めて記録するのがドメイン実装の仕事です。

### 3. Vitest の基本

```bash
npm install -D vitest @vitejs/plugin-react
```

```ts
// vitest.config.ts — @/ エイリアスを tsconfig と揃えるのを忘れずに
export default defineConfig({
  test: { environment: "node", include: ["__tests__/unit/**/*.test.ts"] },
  resolve: { alias: { "@": path.resolve(__dirname) } },
});
```

```ts
// __tests__/unit/indicators.test.ts
import { describe, expect, it } from "vitest";
import { sma } from "@/lib/indicators/sma";

describe("sma", () => {
  it("期間3の移動平均を手計算値と照合する", () => {
    expect(sma([1, 2, 3, 4, 5], 3)).toEqual([null, null, 2, 3, 4]);
  });
});
```

`npm test`（= `vitest run`）で全件実行。**テスト名は日本語で「仕様」を書く**のが本アプリの流儀です。テスト一覧がそのまま仕様書として読めるようになります。

### 4. テスト設計 — 何を書けばいいか

やみくもに書くのではなく、3 種類を意識します。

| 種類 | 考え方 | 本アプリでの実例 |
|------|-------|----------------|
| **既知値照合** | 手計算・電卓で出せる答えと比べる | `sma([1..5], 3) → [null,null,2,3,4]` |
| **境界値** | 「ぎりぎり」の入力で正しいか | PER 15.0 は合格、15.1 は不合格 / データ数が期間ちょうど・期間未満 |
| **性質（不変条件）** | 具体値でなく「常に成り立つこと」 | 上昇し続ける系列なら RSI は 100 / 下落し続ければ 0 / 勝率は決済がなければ null |

さらに、**人工データを設計してシナリオを検証する**技法があります。バックテストのテストがその典型です:

```ts
// 「100→120→150→200 と上がる株を初日に買って持ち続けたら +100% で Buy&Hold と一致するはず」
const prices = toPrices([100, 120, 150, 200]);
const result = runBacktest(prices, [signal(0, "buy")], fullRange);
expect(result.totalReturnPct).toBeCloseTo(100);
expect(result.buyHoldReturnPct).toBeCloseTo(100);
```

答えが暗算できる人工データを作れれば、複雑なロジックもテストできます。

### 5. テストしやすさは設計で決まる

ゴールデンクロス判定（SMA5 が SMA25 を上抜け）をテストしたいとき、5/25 を関数内に固定すると「26 本以上のデータを用意して交差を起こす」面倒なテストになります。**期間を引数（デフォルト付き）にする**と、期間 2/3 の 7 本のデータでテストできます。

```ts
export function evaluateSmaCross(prices: PricePoint[], shortPeriod = 5, longPeriod = 25): Signal[]
// テストでは evaluateSmaCross(prices, 2, 3) — 小さなデータで交差を作れる
```

「テストが書きにくい」と感じたら、それは設計改善のシグナルです。

### 6. リグレッション防止という価値

本アプリはテスト 70 件を、機能追加のたび・リファクタのたびに全実行しています。ダークモード対応やバッジ共通化のような「壊してないはず」の変更でも、70 件が 3 秒で「壊れていない」と保証してくれる——これが単体テストの日常的な価値です。手動更新するデータ（銘柄リスト）の整合性チェックをテストにした例もあります（`__tests__/unit/nasdaq100.test.ts`: 重複・セクター名の誤字を検出）。
