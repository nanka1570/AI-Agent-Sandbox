# 第1章 全体設計と責務分離

## 学習目標

- アプリを「層」に分ける理由を、自分の言葉で説明できる
- 「純粋関数」とは何か、なぜドメインロジックを純粋関数にするのかを説明できる
- 閾値や設定値を定数として一元管理する習慣を身につける

## facility-management との接続

facility-management Phase 1 では、おそらく「ページやコンポーネントの中から Supabase を直接呼ぶ」構造だったはずです。画面数が少ないうちはそれで十分ですが、stock-signal-app には次の事情があり、同じやり方では破綻します。

- **計算ロジックが多い**: SMA・RSI・ボリンジャーバンド・バックテスト・ファンダ判定。これらを画面のコードに混ぜると、正しさを確認する手段が「画面を見て目視」しかなくなる
- **外部 API がいつか壊れる**: Yahoo Finance は非公式 API。壊れたとき、呼び出しが 20 ファイルに散らばっていたら全部直すことになる

## 本編

### 1. 層の分け方 — 「知っていいこと」で分ける

stock-signal-app のディレクトリは、技術ではなく**責務**で分かれています。

| 層 | 場所 | 知っていいこと | 知ってはいけないこと |
|----|------|--------------|-------------------|
| 画面 | `app/` `components/` | クエリ層の結果の形 | SQL・外部 API の仕様 |
| クエリ層 | `lib/queries.ts` | DB と計算ロジック | 画面の都合・外部 API |
| 計算ロジック | `lib/indicators/` `lib/signals/` `lib/backtest/` `lib/fundamentals/` | **数値の配列だけ** | DB・API・画面（何も知らない） |
| データ層 | `lib/data/` | 外部 API と DB | 画面・計算ロジック |
| 定数 | `lib/constants/` | 何も依存しない | — |

重要なのは矢印の向きです。**依存は常に「画面 → クエリ → 計算/データ → 定数」の一方向**。計算ロジックが DB を import した瞬間、その関数は「DB がないとテストできない関数」になります。

### 2. 純粋関数 — この設計の心臓部

**純粋関数**とは、次の 2 つを満たす関数です。

1. 同じ入力には必ず同じ出力を返す（時刻・乱数・DB の中身に左右されない）
2. 外部に影響を与えない（DB 書き込み・API 呼び出し・グローバル変数の変更をしない）

```ts
// 純粋関数: 配列を受け取り配列を返すだけ。DB も API も知らない
export function sma(values: number[], period: number): (number | null)[] { ... }

// 純粋でない関数: DB に依存する。テストには DB が必要になる
export async function smaForStock(ticker: string): Promise<number[]> {
  const rows = await prisma.dailyPrice.findMany({ where: { ticker } }); // ← これが混ざると
  ...
}
```

純粋関数にする利点は 3 つあります。

- **テストが一瞬で書ける**: `expect(sma([1,2,3,4,5], 3)).toEqual([null, null, 2, 3, 4])` — DB のセットアップ不要
- **再利用できる**: 同じ `sma()` をダッシュボード・詳細ページ・バックテストの 3 箇所から使える
- **バグの切り分けが速い**: 画面がおかしいとき「計算が悪いのか、データが悪いのか、表示が悪いのか」を層ごとに切り分けられる

stock-signal-app では「DB から取ってくる」処理と「計算する」処理を必ず分離しています。`lib/queries.ts` が DB から配列を取り出し、純粋関数に渡し、結果を画面用の形に組み立てる——この「組み立て役」がクエリ層です。

### 3. 外部依存の隔離 — 壊れる前提で設計する

Yahoo Finance のような非公式 API は「いつか壊れる」前提で使います。対策は単純で、**そのライブラリを import するファイルを 1 つに限定する**ことです。

```
lib/data/yahoo.ts   ← yahoo-finance2 を import するのはこのファイルだけ
lib/data/sync.ts    ← yahoo.ts の関数を呼ぶ（ライブラリは知らない）
lib/queries.ts      ← DB しか見ない（API があることすら知らない）
```

壊れたときに直すのは `yahoo.ts` の関数 2 つだけ。戻り値の型（`PriceRow[]` など）を変えなければ、他のファイルは 1 行も変更不要です。

### 4. 定数の一元管理 — マジックナンバーを書かない

「RSI が 30 以下で買い」「乖離 +15% で警戒」のような閾値をコードのあちこちに直書きすると、後で「25 に変えたい」となったとき漏れが出ます。stock-signal-app では判定閾値をすべてファイル先頭の `export const` に集め、**コメントで根拠**を書いています。

```ts
// ── 判定閾値（判断基準に基づく。変更する場合はここだけ直す） ──
export const VOLUME_SURGE_RATIO = 2;  // 出来高が20日平均の2倍以上 = 急増
export const KAIRI_WARN_PCT = 15;     // 25日線から +15% 以上の乖離 = 天井警戒
```

実際にこの開発では「直近 5 営業日」という数値が 2 ファイルに直書きされていてレビューで指摘され、定数に一元化しました。**同じ数値が 2 箇所に現れたら定数化のサイン**です。

## 見本の場所

- 層の全体像: `stock-signal-app/lib/` のディレクトリ構成と `README.md` の「プロジェクト構成」
- 純粋関数の典型例: `lib/indicators/sma.ts`（20 行、依存ゼロ）
- 組み立て役: `lib/queries.ts`（DB → 純粋関数 → 画面用の型）
- 定数の一元管理: `lib/signals/technical-state.ts` の冒頭、`lib/signals/evaluate.ts` の冒頭
