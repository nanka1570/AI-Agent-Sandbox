# 第7章 E2E テスト（Playwright）

## 学習目標

- 単体テストと E2E テストの役割分担を説明できる
- 「外部 API に依存しない E2E」をシードデータとテスト用 DB で実現できる
- Playwright のセレクタの選び方（getByRole 優先）と典型的な失敗を知る

## facility-management との接続

facility-management の動作確認は「ブラウザで自分で触る」でした。E2E テストはそれの自動化です——「ページを開く → ボタンを押す → 表示を確認する」を毎回、機械が数秒でやってくれます。第4章の単体テストが「計算が正しいか」を守るのに対し、E2E は「**配線が繋がっているか**」（DB → クエリ → 画面 → 操作の一気通貫）を守ります。

## 本編

### 1. 何を E2E にするか — 少数精鋭

E2E は単体テストより遅く壊れやすいので、**画面ごとに「主要な 1 本の道」だけ**を書きます。本アプリは 3 件だけです:

1. ダッシュボードに銘柄一覧・タイプ分類が表示される
2. 詳細ページにチャート・ファンダ判定・メモ欄が表示される
3. バックテストを実行すると結果が表示される

細かい分岐（境界値・エラーケース）は単体テストの仕事。**ピラミッド**（単体多数・E2E 少数）を保ちます。本アプリの比率は 70 : 3 です。

### 2. 最大の設計問題: 外部 API に依存させない

素朴に書くと「E2E 実行 → 同期ボタン → Yahoo Finance に 117 回アクセス」となり、遅い・不安定・実行するたび結果が変わる、の三重苦になります。解決は 2 段構えです。

**(a) テスト用 DB の分離** — SQLite はファイルなので、環境変数で切り替えるだけ（第2章の伏線回収）:

```ts
// playwright.config.ts
webServer: {
  command: "npm run dev -- -p 3100",             // 開発サーバーと別ポート
  env: { DATABASE_FILE: "prisma/test.db" },      // 開発用 dev.db を汚さない
  reuseExistingServer: false,
},
```

**(b) シードスクリプト** — 検証したい状態を**人工データで作り込む**。ここが腕の見せ所です:

```
scripts/seed-e2e.ts の設計（意図が全部データに込められている）:
- 価格系列: 前半 250 日下降 → 後半 150 日上昇
    → 必ずゴールデンクロスが発生する = シグナル表示のテストが安定して書ける
- AAPL のファンダ: 高 ROE・高マージンの値
    → タイプ分類が「実績先行の王者型」になる = 分類表示をテストできる
- ベンチマーク(QQQ): 最終日だけ下落させる
    → 個別株の「逆行高」バッジが必ず出る
```

「テストしたい表示から逆算してデータを設計する」——第4章の人工データ設計と同じ思考です。実行順は `migrate deploy → シード → playwright test` を npm script に固定します（見本: package.json の `test:e2e`）。

### 3. テストの書き方とセレクタ

```ts
import { expect, test } from "@playwright/test";

test("ダッシュボードに銘柄一覧が表示される", async ({ page }) => {
  await page.goto("/");
  await expect(page.getByRole("heading", { name: "米国テック株シグナル一覧" })).toBeVisible();
  await expect(page.getByRole("link", { name: "AAPL" })).toBeVisible();
  await expect(page.getByText("データ不足")).toHaveCount(0);  // 「ないこと」の検証
});
```

セレクタの優先順位: **`getByRole`（見出し・ボタン・リンク）> `getByLabel` > `getByText`**。role ベースは「ユーザーに見えているもの」で選ぶためリファクタに強く、副産物としてアクセシビリティ（aria-label 等）が整います。

**典型的な失敗（実話・2 回踏んだ）**: `strict mode violation` — セレクタが 2 要素以上にマッチするとエラーになります。本アプリでは「Buy & Hold」が説明文と結果カードの両方にあって落ちました。対処は `{ exact: true }`、`getByRole("cell", ...)` のような絞り込み、または `.first()`。エラーメッセージにマッチした全要素が表示されるので、それを読めば直せます。

### 4. 運用の注意（本アプリで実際に踏んだもの）

- **ブラウザの用意**: WSL では `npx playwright install --with-deps` が sudo を要求して失敗する。`npx playwright install chromium` でブラウザだけ入れ、不足ライブラリは `apt-get` で個別に入れる（詳細は `docs/maintenance.md`）
- **開発サーバーと衝突する**: Next.js 16 は同一ディレクトリで dev サーバーを二重起動できない。E2E 前に開発用サーバーを止める
- **UI 文言の変更でテストが割れる**: 見出しを変えたら E2E も直す。これは欠点ではなく「画面とテストが同期している」証拠。だからこそ E2E は少数精鋭に保つ

## 演習

1. **[設計]** facility-management に E2E を入れるとしたら、まず守るべき「1 本の道」は何か。3 画面分を 1 行ずつ書く（例: ログイン → カレンダーで空きセルをクリック → 予約が表示される）
2. **[シード設計]** 演習 1 のテストに必要なシードデータを設計する。「予約済みのセル」「空きセル」「キャンセル済み予約」がそれぞれ最低 1 つは画面に現れるようにデータを決める
3. **[実装]** これまでの演習アプリ（天気 or Book）に Playwright を導入し、「一覧ページに件数が表示される」の 1 本を通す。テスト用 DB の分離（環境変数）まで含めること
4. **[体験]** わざと 2 要素にマッチするセレクタを書いて strict mode violation を起こし、エラーメッセージから 3 通りの直し方（exact / role 絞り込み / first）を試す
