# 第3章 外部 API 連携とキャッシュ

## 学習目標

- 外部 API のデータを DB にキャッシュする設計を、理由込みで説明できる
- 「差分同期」と「冪等性」を実装できる
- TTL（有効期限）付きキャッシュを DB とメモリの 2 通りで実装できる

## facility-management との接続

facility-management の データはすべて「自分の DB」にありました。stock-signal-app のデータは**他人のサーバー**（Yahoo Finance・SEC）にあります。他人のサーバーには次の制約があり、これがこの章の設計をすべて決めます。

- 呼びすぎると弾かれる（レート制限）
- 遅い（1 銘柄数百 ms × 117 銘柄 = 画面表示に使えない）
- いつか仕様が変わって壊れる（特に非公式 API）

## 本編

### 1. 基本方針: 「表示のたびに API」ではなく「同期して DB から表示」

```
[悪い設計] 画面表示 → その場で API 117 回 → 遅い・レート制限・API 死 = 画面死
[本アプリ] 「データ更新」ボタン → API → DB に保存
           画面表示 → DB だけ読む（速い・オフラインでも動く・API が死んでも過去分は見える）
```

つまり**画面と API を直結しない**。間に DB を挟むだけで 3 つの問題が全部解決します。代償は「データが最新とは限らない」ことですが、日足の株価は 1 日 1 回更新できれば十分です。**データの鮮度要件を最初に確認する**のがこの種の設計の出発点です。

### 2. 差分同期 — 毎回全部取らない

初回は 5 年分（約 1,250 行）必要ですが、2 回目以降に必要なのは「前回以降の数日分」だけです。

```
アルゴリズム（lib/data/sync.ts）:
1. DB からその銘柄の最新日付を取る（findFirst + orderBy date desc）
2. 最新日付があれば「その日以降」だけ API に要求。なければ 5 年分
3. 取れた行を DB に保存
```

**罠（実話・レビューで発見）**: 「最新日の翌日から」取ると、取引時間中に同期した日の**途中の価格が確定値として残り続け**ます。対策は「最新日を**含めて**取り直し、その日の行は削除→再挿入」。数行の違いですが、放置するとその銘柄の指標が恒久的にずれる類のバグです。

### 3. 冪等性 — 何度実行しても安全にする

**冪等（べきとう）**: 同じ操作を 2 回実行しても、1 回のときと結果が同じである性質。同期処理は途中で失敗して再実行されるものなので、冪等でないと再実行のたびに行が重複します。

本アプリでの実現手段は 2 つの合わせ技です。

1. **複合主キー**（第2章）: `@@id([ticker, date])` により同じ日の行は物理的に 2 つ入らない
2. **削除→挿入をトランザクションで**: `prisma.$transaction([deleteMany, createMany])` — 途中で失敗しても中途半端な状態にならない

「失敗した銘柄だけ再実行」ボタンが安全に作れるのは、この冪等性があるからです。

### 4. 1 リクエスト = 1 銘柄 — 長時間処理の分割

117 銘柄 × 5 年分を 1 つの API Route で処理すると数分かかり、タイムアウトし、進捗も出せません。本アプリの解法:

```
サーバー: POST /api/sync/[ticker] は「1 銘柄だけ」処理する（数秒で返る）
クライアント: for ループで 117 回直列に fetch。完了数 / 117 がそのまま進捗バーになる
```

サーバーを賢くするのではなく、**仕事を小さく割ってクライアントに主導権を持たせる**。失敗銘柄の記録・再実行も自然に書けます（見本: `components/sync-panel.tsx`）。

### 5. TTL キャッシュ — 「一定時間は前回の結果を使う」

株価ほど頻繁に変わらないデータ（財務指標: 四半期ごと、VIX: 分単位でも 1 時間で十分）は、**取得時刻を一緒に保存して期限内なら API を呼ばない**方式にします。

```ts
// DB キャッシュ版（lib/data/fundamentals.ts）: fetchedAt 列と比較
const cached = await prisma.fundamental.findUnique({ where: { ticker } });
if (cached && Date.now() - cached.fetchedAt.getTime() < TTL_MS) return cached;
try {
  const fresh = await fetchFromApi(ticker);
  return await prisma.fundamental.upsert({ ... });
} catch {
  return cached;   // ← API が落ちていたら「期限切れでも」前回値を返す。全滅よりまし
}
```

```ts
// メモリキャッシュ版（lib/data/market.ts）: 再起動で消えてよいものはこれで十分
let cache: { value: number | null; fetchedAt: number } | null = null;
```

使い分け: **再起動後も残したい・銘柄ごとに持ちたい → DB。プロセス内で共有できれば十分 → メモリ変数**。

### 6. 変換層 — 外部の形を家の中に持ち込まない

API のレスポンスをそのまま DB や画面に流すと、API の仕様変更が全体に波及します。本アプリは境界で必ず自分の型に変換します。

```
yahoo-finance2 の生レスポンス → transform.ts の mapChartQuotes() → PriceRow（自分の型）
```

変換層でやること（見本: `lib/data/transform.ts`）: null 混じり行の除外、日付の UTC 正規化、重複日の解決。**この変換だけは純粋関数にできる**ので、外部 API 連携の中で唯一しっかり単体テストできる部分です（実際に 6 件のテストがあります）。

### 7. API キーの管理（第8章の伏線）

キーが必要な API は、キーを**環境変数**（`.env.local`、git 管理外）に置き、`.env.example`（値なしの雛形）だけをコミットします。「未設定でもアプリは壊れず、その機能だけ無効化」という作りにすると、他人（未来の自分）がセットアップしやすくなります。

## 見本の場所

- 差分同期と冪等性: `lib/data/sync.ts`（50 行。この章の要点が全部入り）
- 変換層: `lib/data/transform.ts` とそのテスト `__tests__/unit/transform.test.ts`
- TTL キャッシュ: `lib/data/fundamentals.ts`（DB 版）、`lib/data/market.ts`（メモリ版）
- 1 リクエスト 1 銘柄: `app/api/sync/[ticker]/route.ts` + `components/sync-panel.tsx`

## 演習

無料でキー不要の公開 API（例: `https://api.open-meteo.com/` の天気 API）を使って、ミニ同期システムを作ります。

1. **[基本]** Prisma に `DailyWeather { city, date, tempMax }`（複合主キー）を作り、「過去 7 日分を取得して保存する」関数を書く
2. **[差分]** DB の最新日以降だけ取得するように改造する。2 回連続で実行して 2 回目がほぼ即座に終わること、行が重複しないことを確認する
3. **[冪等]** 実行中に Ctrl+C で中断 → 再実行しても壊れないことを確認する。壊れたなら、削除→挿入のトランザクション化を検討する
4. **[変換層]** API レスポンスの型をそのまま使っている箇所を探し、自分の型 + 変換関数に分離する。変換関数に単体テストを 3 つ書く（null が来たら？ 重複したら？）
